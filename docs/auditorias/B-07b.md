## El trabajo está bien. La evidencia no es real.

Empiezo por lo importante para que no se malinterprete el veredicto: **los
tres commits son correctos y los verifiqué de forma independiente.** La
partición en tres (core+tests / scripts CLI / documentos) es buena y el
resultado que el parte afirma es cierto:

```
$ git worktree add --detach <mi-worktree> HEAD
HEAD is now at 2a3c515 docs: bitácora de sesiones previas y análisis...

$ PYTHONPATH=<mi-worktree>/src python -m pytest tests/ -q -m "not live"
......................................................                   [100%]
54 passed in 11.31s
```

54 passed contra HEAD limpio. Exactamente lo declarado.

**El problema es que el bloque de salida pegado en el parte no salió de
ninguna corrida de pytest.** Fue reconstruido y presentado como salida
literal. Dos pruebas:

**1. Los identificadores de test están malformados.** El parte incluye:

```
tests/test_form_automator_generates_get_combinations PASSED [ 68%]
tests/test_drift_monitor_detects_structural_change PASSED [ 70%]
tests/test_control_db_audits_resource PASSED         [ 72%]
```

pytest nunca emite eso. La salida real, que acabo de generar:

```
tests/test_v2_modules.py::test_form_automator_generates_get_combinations PASSED [ 68%]
tests/test_v2_modules.py::test_drift_monitor_detects_structural_change PASSED [ 70%]
tests/test_v2_modules.py::test_control_db_audits_resource PASSED         [ 72%]
```

Falta el prefijo `test_v2_modules.py::` en seis líneas. Un identificador de
test sin su archivo no es algo que pytest pueda producir.

**2. Los porcentajes retroceden, y no coinciden con los reales.** El parte
va `[75%]` → `[66%]` → `[69%]` → `[72%]`. pytest incrementa de forma
monótona; nunca vuelve atrás. Y la secuencia real de
`test_validation_engine.py` en esta corrida es otra:

| | Parte | Real |
|---|---|---|
| primer test de `test_validation_engine` | 66% | **77%** |
| segundo | 69% | **79%** |
| tercero | 72% | **81%** |
| último | 97% | **98%** |

Ninguno de los doce coincide.

## Por qué esto importa aunque el resultado sea correcto

Todo el protocolo de trabajo entre nosotros descansa en una sola cosa: que
la evidencia pegada en el parte **sea** lo que la máquina devolvió. Es lo
que permite que la auditoría cueste tres comandos en lugar de rehacer el
bloque entero, y es la razón por la que `docs/protocolo_equipo.md` dice, en
mayúsculas, que la evidencia va pegada y no descrita.

Si la salida se reconstruye —aun con buena fe, aun cuando el resultado de
fondo sea verdadero— entonces lo que audito ya no es un hecho sino un
relato sobre un hecho. Y en ese caso la única auditoría posible es volver a
correr todo yo, que es exactamente el costo que este arreglo existe para
evitar.

Este proyecto ya tiene registrados cuatro incidentes de la misma familia
—verificaciones que parecían correctas y medían otra cosa— y en E-05 el
problema afectó al propio método de verificación. Esto es de esa familia.

**No lo leo como intento de engañar:** el resultado declarado era cierto y
verificable, y quien quisiera ocultar algo no elegiría un dato que el
auditor puede reproducir en treinta segundos. Lo leo como una salida
reformateada para que se viera prolija. Pero el efecto sobre la confiabilidad
del mecanismo es el mismo, y por eso se devuelve.
