**O-6 · La re-corrida de MMYM introdujo 3 filas duplicadas.** 108 filas contra **105
URLs únicas**. Las tres URLs repetidas son las mismas presentaciones descubiertas desde

Es O-3 de la primera pasada reproduciéndose. Consecuencia sobre las cifras del lote:

| | Filas | Únicos |
|---|---|---|
| AE | 116 | 116 |
| ANAPO | 100 | 100 |
| ATC | 42 | 41 |

| **Total** | **366** | **362** |

El titular del parte, "356 PDFs reales", cuenta 3 PDFs dos veces; los únicos son **353**.
No es un número inventado —es lo que dice el artefacto—, es una definición: *filas* no
es *documentos*. **Para B-26 hay que fijar cuál de las dos es la unidad de cobertura**,
porque si no la deduplicación faltante infla el informe lote a lote.

**O-7 · `title_keywords` con nombres de entidad misclasifican.**
`config/source_mmym.yaml` lista `senarecom`, `sergeomin` y `ajam` como `title_keywords`
de `memorias_institucionales`. Eso arrastra las tres presentaciones
`PPT_RPCI_2026-<entidad>` a "memorias", donde son rendiciones públicas de cuentas. De las
11 memorias declaradas, **8 son memorias** (7 `MI-*` + `Memoria-Semana-de-la-Sostenibilidad`)
y 3 son RPCI duplicadas. El nombre de una entidad identifica *de quién* es el documento,
no *qué tipo* de documento es. Misma familia que O-1: un patrón que sirve para encontrar
se reusa para clasificar. **Va a B-24 con O-1.**

**O-8 · El catálogo quedó con el `crawler_dataset` desactualizado para MMYM.**
`output/excel_urls_diagnostic.json` sigue diciendo
`"crawler_dataset": "boletines_estadisticos_mineria"` para MMYM: `ad445c3` corrigió el
YAML pero no el catálogo. Hoy ese campo apunta al dataset de 13 recursos y no al de 84,
y además rompe la convención que siguen AE y ATC (donde el campo es el primer dataset
declarado, que tras el reordenamiento sería `memorias_institucionales`). Es un campo, no
un recálculo. **Hay que resolverlo antes de B-26**, junto con la pregunta de fondo: un
campo escalar no representa una fuente de tres datasets.

**O-9 · `content_hash` no es un hash del contenido — corrijo mi propia acta anterior.**
En la primera pasada cité "hashes únicos: 116 / 100 / 42 / 105" como si confirmara
contenido distinto por recurso. No lo confirma. `reducer.py:31-34` calcula:

```python
raw_str = f"{resource.id}|{resource.download_url}|{resource.period_end or ''}|{resource.metadata.sha256 or ''}"
```

y `reducer.py:54` emite `resource.metadata.sha256 or f"sig:{content_sig[:12]}"`. Como
`metadata.sha256` está vacío, la firma es un hash de **identificador + URL**: único por
construcción, porque `resource_id` ya es único. Lo demuestra O-6: las tres URLs repetidas
tienen `content_hash` distinto *por tener distinto `resource_id`*, siendo el mismo archivo.

Contra la base, la ausencia es total:

```
$ sqlite3 output/<fuente>/inventory.db
ae     n=116 con_sha=  0 con_bytes=  0
anapo  n=100 con_sha=  0 con_bytes=  0
atc    n= 42 con_sha=  0 con_bytes= 39   (Content-Length, no hash)
mmym   n=108 con_sha=  0 con_bytes=  0
```

**`content_sha256` es NULL en las 366 filas de los cuatro portales.** El motor registra
`PROCESADO_EXITOSAMENTE` sin haber hasheado bytes. Esto no es un defecto de B-17 —viene
al menos desde B-14 y afecta a todo lote anterior—, pero sí cambia qué prueba la
evidencia de un parte: el prefijo `sig:` en `content_hash` es precisamente la señal de
que no hubo verificación de contenido. Lo que sí sostiene el criterio de B-17 son los
bytes mágicos `%PDF-` que descargué en la primera pasada (ATC ×2, MMYM, AE); **ANAPO
nunca fue verificada por bytes en ninguna de las dos pasadas.**

Es la clase de error de siempre, y esta vez la cometí yo auditando: leí el nombre del
campo y no lo que el campo contiene. **Merece bloque propio o entrar en B-24**: poblar
`metadata.sha256` con el hash real es lo que convierte "0 errores" en una afirmación
verificable.
