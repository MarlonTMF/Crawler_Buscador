## 2. Hallazgos que motivan la devolución

### H-1 · El registro de intentos de recuperación nunca se carga: la escalera de B-54 está desconectada

`scripts/gestionar_ciclo_vida.py:81` itera `data.get("recovered_periods", [])`.
Esa clave no existe en ninguno de los dos artefactos de B-54:

```
$ python -c "...json.load(...)"
docs/entregas/recuperaciones_b54.json  total_recovered= 3 len(recoveries)= 3 recovered_periods? False
docs/entregas/recuperaciones_b54b.json total_recovered= 3 len(recoveries)= 3 recovered_periods? False
```

Consecuencia medida sobre el artefacto commiteado:

```
$ python -c "... sum(1 for x in r['datasets'] if x['recovery_attempts_log'])"
logs no vacios: 0
```

**Los 21 registros tienen el log de intentos vacío.** El `try/except` de
`:90-91` no salta porque el JSON se parsea sin error: es exactamente la clase de
fallo que `CLAUDE.md` describe —no produce ningún error visible y devuelve un
resultado sin verificar—.

Hay un **segundo defecto independiente** en la misma función: `:87` escribe
`"success": True` fijo para todo intento. La invariante de
`lifecycle.py:158-165` exige `all(not att.get("success"))`, así que aun
arreglando la clave, ningún dataset podría nunca cumplir `ladder_exhausted`.
Con los dos defectos, **la rama `HISTORICO` es código muerto desde datos
reales**: el `HISTORICO: 0` del parte no es el resultado de una evaluación que
podría haber dado otro número.

Esto rompe la mitad del criterio del plan que dice «y quede registrado qué se
intentó». Hoy no queda registrado nada. La dirección del error es la segura —no
archiva de más, archiva de menos—, y por eso el bloque no está mal concebido;
pero la capacidad que anuncia el mensaje de commit («archivado justificado») no
es operable de punta a punta.

**Corrección pedida:** leer `recoveries`, derivar `success` del campo `status`
real del registro (`RECOVERED` → éxito; los fallos hay que emitirlos desde
`recovery_ladder.py` si hoy no se persisten — si no se persisten, decilo en el
parte en vez de sintetizarlos), y agregar un test que cargue los JSON reales de
B-54 y afirme que al menos un dataset queda con `recovery_attempts_log` no
vacío. Sin ese test el defecto vuelve: los 7 tests actuales pasan con la
función completamente rota, porque ninguno toca el script.

### H-2 · `transition_date` es la fecha de la corrida, no la fecha del cambio de estado

El plan pide «la regla de transición **y la fecha en que cambió**»
(`plan_bloques_fase4.md:295-296`). `lifecycle.py:100` fija
`now_iso = datetime.now(...)` y las cinco ramas lo escriben sin excepción; el
script nunca lee el reporte anterior y pasa `previous_state=None` en todas las
llamadas (`gestionar_ciclo_vida.py:186-192`). Verificado:

```
$ python scripts/gestionar_ciclo_vida.py
$ git diff --numstat docs/entregas/ciclo_vida_datasets.json
22      22      docs/entregas/ciclo_vida_datasets.json
# y el diff filtrado sin transition_date/timestamp está vacío:
$ git diff ... | grep "^[-+]" | grep -v "transition_date\|timestamp"
(sin coincidencias más allá de las cabeceras del diff)
```

Los 21 estados son idénticos y las 21 fechas cambiaron. Un campo que se mueve
cuando nada se movió no sirve para auditar cuándo algo se movió, que es
literalmente para lo que el plan lo pide. `previous_state` está en el modelo,
en los tests y en el JSON, pero en producción vale `None` en los 21 registros.

**Corrección pedida:** cargar el reporte anterior (si existe), y conservar
`transition_date` + poblar `previous_state` cuando el estado no cambió respecto
de la corrida previa. Con un test que corra dos veces y afirme que la fecha no
se movió en la segunda.

### H-3 · La evidencia del §2.3 no es la salida del comando y sus cifras por portal no reproducen

El protocolo es explícito: «se pega la salida real del comando. Una descripción
de la salida no es evidencia». El §2.3 presenta una tabla markdown construida a
mano. Al correr el comando, tres cifras no coinciden:

| Cifra del parte | Real (salida del script) |
|---|---|
| INE: 10 datasets (9 VIGENTE) | **8** datasets (7 VIGENTE) |
| ASFI: 3 datasets (2 VIGENTE) | **5** datasets (4 VIGENTE) |
| `balance_general`: «2 períodos atrasado» | **8** períodos (`tol=2`) |
| BCB: 5 datasets, todos VIGENTE | 5, correcto |
| Totales 21 / 16 / 2 / 3 / 0 | correcto |

Los totales cuadran por casualidad aritmética (10+3 = 8+5), que es justo por qué
esta clase de error pasa desapercibida. Cae en dos de las condiciones de fallo
del protocolo a la vez: evidencia parafraseada y un número que no se reproduce
con el comando del parte.

**Corrección pedida:** pegar la salida cruda del script (las 21 filas + la línea
de resumen), sin reformatear.

## 3. Observaciones (no bloquean, pero se anotan)

**O-1 · El parte describe un modelo que no es el que se commiteó.** §1 dice
«`DatasetLifecycleRecord`: Modelo **Pydantic inmutable**/serializable».
`lifecycle.py:47-60` es un `@dataclass` plano de la librería estándar, mutable
(sin `frozen=True`), y el módulo no importa Pydantic. La forma elegida está
bien; el problema es afirmar una propiedad —inmutabilidad— que el auditor no
puede dar por buena y que el código no tiene.

**O-2 · Cotejo de propuestas de herencia por subcadena.** `lifecycle.py:114-116`
acepta la correspondencia con `portal.lower() in orig_p` y
`dataset_id.lower() in orig_ds`. Una propuesta `ACEPTADA` para
`cuentas_nacionales_pib_trimestral` migraría también a `cuentas_nacionales_pib`.
D-18 descarta explícitamente la correlación léxica como criterio
(«'CADEX' y 'CADEXCO' son léxicamente casi idénticas y son entidades
distintas»); acá el riesgo es menor porque la propuesta ya pasó por aprobación
humana, pero el cotejo debería ser igualdad exacta de `(portal, dataset_id)`.
Hoy no tiene efecto medible: las 3 propuestas de B-55 están `RECHAZADA` y hay
0 `ACEPTADA`, así que la rama `MIG_D18_ACEPTADA` no se ejerce con datos reales
—solo en test—.

**O-3 · 7 de los 16 `VIGENTE` son datasets sin modelo de período.** Los que
salen con `Último Per. = -` (`memorias_institucionales`,
`gestion_administrativa_financiera`, `estadisticas_sociales_demograficas`,
`planes_estrategicos`, `documentos_institucionales_otros`,
`memoria_institucional`, `mercado_valores`,
`instituciones_financieras_desarrollo`) tienen `tolerance=0` y
`delay_periods=0`, y entran por `:136` (`0 <= 0`) con la justificación «Serie
vigente: retraso de 0 período(s) dentro de la tolerancia permitida (0)». Tienen
recursos reales (entre 8 y 386), no están vacíos, pero ahí `VIGENTE` significa
«no se evalúa vigencia», no «al día». Conviene un quinto valor o una marca
`sin_periodicidad`, para que el reporte no lea como que 16 series están al día
cuando 9 lo están y 7 no se miden. El parte tampoco hace esa distinción.

**O-4 · Falta la verificación contra HEAD limpio.** Corresponde a todo bloque
que commitea Python. La corrí yo y salió en verde (§1); pero el parte debe
incluirla, no el acta.

**O-5 · Seguimiento sin actualizar.** `docs/plan_bloques_fase4.md:364` sigue
marcando B-56 como «Pendiente» y con la columna Real vacía. Lo actualizo al
cerrar la re-entrega, no antes.

**O-6 · Estado del árbol.** Mi re-corrida del script dejó
`docs/entregas/ciclo_vida_datasets.json` modificado (solo los 22 timestamps). No
lo restauré porque el comando de restauración requería aprobación; queda para
descartar con `git checkout HEAD -- docs/entregas/ciclo_vida_datasets.json` antes
de retomar el bloque.
