## 1. Qué se hizo y Criterios de Aceptación Cumplidos

En este bloque se resolvió la brecha de resiliencia frente a bloqueos WAF / Cloudflare descrita en la decisión **D-03**: permitir que una fuente que rechaza peticiones HTTP simples con código `403 Forbidden` (por huella TLS o desafío JavaScript de protección contra bots) sea reintentada de forma automática y transparente mediante un navegador real (`HeadlessFetcher` con Playwright), sin requerir intervención manual ni reconfiguraciones ad-hoc.

### Criterio 1: Activación condicional estricta ante 403 (eficiencia de cómputo)
- Se incorporó en `HttpFetcher` el parámetro `auto_headless_on_403: bool = True`.
- En `fetch_html(url)`: el cliente HTTP estándar (`requests.Session`) ejecuta la solicitud liviana ordinaria. Si el servidor responde `200`, `404`, `500` o cualquier código distinto de `403`, **nunca** se instancia ni se invoca el navegador Playwright, preservando la velocidad del crawler y evitando el sobrecosto de renderizado en páginas que no lo necesitan.
- Si y solo si la respuesta del servidor es HTTP `403` y `auto_headless_on_403` está habilitado, se dispara de forma condicional el método interno `_fetch_html_via_headless(url)`.
- Si el usuario o una configuración específica desea apagar este comportamiento, puede fijar `auto_headless_on_403=False`.

### Criterio 2: Registro auditable formal como "resuelto vía headless"
El reintento exitoso no se oculta como un 200 genérico; deja huella formal de trazabilidad en todos los niveles:
1. **Logging estructurado:** Emite `[INFO] URL <url> respondió 403 en HTTP simple -> resuelta exitosamente vía headless (status <status>)`.
2. **Estado en el Fetcher:** Registra la URL en `self.resolved_via_headless_urls: Set[str]` y levanta la bandera `self.last_fetch_resolved_via_headless = True`.
3. **Diagnóstico / Conectividad (`validate_url_access`):** Añade `"browser_fallback_used": True` y `"resolved_via_headless": True` en el diccionario de diagnóstico.
4. **Metadatos de Dominio (`ResourceMetadata`):** Nuevo campo `resolved_via_headless: bool = Field(False)` que queda persistido en los JSONs de exportación (`mapa_<source>.json`).
5. **Trazabilidad de Extracción (`ResourceEvidence`):** El arreglo `evidence.extraction_methods` incluye explícitamente `"resuelto_via_headless"`.

### Criterio 3: Fuente protegida por WAF/Cloudflare pasa a extraer documentos
- Se verificó mediante prueba de integración de extremo a extremo (`test_orchestrator_pipeline_recovers_403_source_via_headless`) que una fuente configurada con `use_playwright: false` cuya semilla responde 403 Forbidden a peticiones directas es rescatada automáticamente por el fallback headless, extrayendo los recursos documentales (`.pdf`) asociados y persistiendo su trazabilidad de auditoría.

### Criterio 4: Cierre formal de la Decisión Técnica D-03 en `docs/decisiones.md`
- Se actualizó `docs/decisiones.md` marcando **D-03 como CERRADA**:
  - Se documentaron las alternativas descartadas (marcar dominio muerto vs. forzar Playwright en todo el crawl vs. configuración manual YAML).
  - Se formalizó la regla operativa: HTTP simple primero, reintento condicional con Chromium headless ante 403, etiquetado formal en auditoría.
  - Se reservó `use_playwright: true` a nivel de YAML únicamente para SPAs dinámicas que requieran JS desde el inicio.
